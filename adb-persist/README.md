# ADB Persist — единый скрипт для Станций

Держит сетевой ADB открытым даже после сброса к заводским.
Скрипт унифицирован: работает через якоря в `onboot.sh`,
не зависит от модели.

## Как это работает

### 1. Разделы и что где лежит

| Раздел / путь | Тип | Сброс | Содержимое |
|---|---|---|---|
| `ubi0:rootfs`, смонтирован как `/` (включая `/system`) | UBIFS, read-only | **переживает** | система, quasar, `onboot.sh`, наш патч и эталон |
| `/bkupgrade` (`ubi1`), `/data` — симлинк в `/bkupgrade/data` | UBIFS, read-write | **стирается** | аккаунт, Wi-Fi, маркеры ADB, `rootkeeper.sh`, логи |
| `/tee` | read-only | переживает | ключи |
| `mtd6`/`mtd7`, u-boot env | — | переживают | recovery, переменные загрузчика |

Главный факт: сброс стирает только пользовательские данные. Всё,
что лежит в `/system`, сброс переживает — на этом и стоит патч.

### 2. Цепочка загрузки

```
u-boot → BusyBox init → /etc/init.d/S99quasar
→ /system/vendor/quasar/onboot.sh start
  → mkdir /bkupgrade/data/quasar, overcommit, чистка OTA-артефактов
  → first-run init (если нет /data/quasar/initialized)
  → chmod 777 ...
  → [ПАТЧ: восстановить маркеры + rootkeeper]   ← вставка, +12 строк
  → yio_iptables_init, set_monotonic_time
  → activate_adb.sh check                        ← решает, стартовать ли adbd
  → чистка старых маркеров, q save-last-monotonic-time
  → run.sh → quasar_launcher2 → maind (platformd/mediad/telemetry/...)
  → touch /data/quasar/initialized
→ [ -x /data/quasar/rootkeeper.sh ] && запустить сторожа фоном
```

### 3. Как включается сетевой ADB (штатно)

```
activate_adb.sh check
  → adb_options.inc: есть хоть один маркер в /data/quasar?
      activate_adb_quasmodrom / activate_adb_sound / activate_adb_glagol
      + activate_network_adb = флаг «именно сетевой режим»
  → нет маркеров → тихий exit 0, adbd НЕ стартует
  → есть → yandex-debugctl adb-net
      → start-stop-daemon → /usr/bin/adbd
      → USB-gadget на станции нет → adbd слушает TCP 0.0.0.0:5555
```

На наших устройствах поверх стоит FORTRESS-обёртка `activate_adb.sh`:
команда `deactivate` превращена в no-op (облако не может выключить ADB),
а `activate` всегда форсирует сетевой режим.

### 4. Что такое сброс

1. Кнопка отключения микрофонов при подаче питания (~5 сек до жёлтого).
2. U-boot видит нажатую кнопку, грузит recovery (`mtd6` + `mtd7`).
3. Recovery стирает всё содержимое `/bkupgrade/data` и перезагружается.
4. Обычная загрузка, но без `/data/quasar/initialized` — срабатывает
   ветка first-run init, станция уходит в онбординг (настройка как новой).

Стирается: аккаунт, Wi-Fi (`wpa_supplicant.conf`), маркеры ADB,
`rootkeeper.sh`, логи. Остаются: весь `/system` (включая рут-моды),
ключи, recovery, u-boot env.

### 5. Почему без патча ADB после сброса мёртв

После wipe маркеров нет → `activate_adb.sh check` выходит с `exit 0` →
adbd не стартует. А сторожа, который мог бы всё починить, тоже нет —
`rootkeeper.sh` сам лежал в стёртом `/data`. Порт 5555 закрыт,
единственный путь назад — физический доступ и повторный рут.

### 6. Что делает патч

12 строк в `onboot.sh`, строго **между** `chmod` и `yio_iptables_init`,
то есть **до** `activate_adb.sh check`, на каждой загрузке:

```sh
RK_SRC=/system/vendor/quasar/rootkeeper.sh.persist   # эталон в /system
RK_DST=/data/quasar/rootkeeper.sh
mkdir -p /data/quasar                                # каталог мог не существовать
touch .../activate_adb_quasmodrom .../activate_network_adb  # маркеры
if [ -f "$RK_SRC" ] && [ ! -x "$RK_DST" ]; then      # keeper пропал?
    cp -f "$RK_SRC" "$RK_DST"                         # восстановить из эталона
    chmod 755 "$RK_DST"
fi
unset RK_SRC RK_DST
```

По строкам:

- `mkdir -p` — после wipe каталога может не быть (first-run его тоже
  создаёт, но дублирование безвредно и делает блок независимым).
- `touch` обоих маркеров — пара `quasmodrom` + `network` означает
  «ADB включён, именно сетевой». Без `network` стоковая логика ушла бы
  в несуществующую USB-ветку.
- Guard `[ -f ... ] && [ ! -x ... ]` — эталон копируется, только если
  он есть в `/system` и keeper в `/data` отсутствует или не
  executable. Ручные правки живого keeper не затираются.
- `unset` — не мусорим в окружении `onboot.sh`.
- Побочный эффект (намеренный): маркеры пересоздаются на каждой
  загрузке, поэтому ADB после установки выключить нельзя — только
  через `uninstall`.

Что происходит при загрузке после сброса с патчем:

```
wipe → reboot → onboot.sh
  → патч: маркеры созданы, keeper восстановлен из /system
  → check: маркеры есть → adb-net → adbd LISTEN :5555
  → последняя строка onboot.sh: keeper запущен, следит за LISTEN
```

На обычных перезагрузках (без сброса) блок — полный no-op: `touch`
лишь обновляет mtime существующих маркеров, `cp` пропускается guard'ом.

### 7. Роль rootkeeper (FORTRESS-KEEPER v3)

Второй рубеж обороны, уже не от сброса, а от всего остального: раз в
60 секунд проверяет маркеры и **LISTEN на :5555** (через
`/proc/net/tcp`, а не `pidof` — так видно даже adbd без сетевого
режима). Если LISTEN пропал — убивает и перезапускает adbd. Именно
поэтому эталон keeper тоже хранится в `/system`: сам keeper живёт
в стираемом `/data`.

### 8. Почему это безопасно для загрузки

- В `onboot.sh` нет `set -e`/`set -u`: упавшая команда не роняет
  скрипт. Худший исход патча — он молча ничего не делает.
- Только базовые команды (`mkdir`/`touch`/`cp`/`chmod`), без сети,
  демонов и новых зависимостей.
- Скрипт установки сверяет: якоря, ровно +13/−0 строк diff'а, `sh -n`
  на хосте и на устройстве, побайтовое сравнение установленного файла
  с проверенной сборкой — и только потом возвращает `/` в `ro`
  (плюс trap на случай обрыва).
- `/system` на наших экземплярах уже правили до нас (FORTRESS) —
  verified boot и проверки целостности не мешают.

## Использование

Требования на хосте: `bash`, `adb`, `patch`. Станция должна быть
доступна по ADB. Устройство задаётся флагом `--device` (по умолчанию
первая станция).

```bash
# Проверить, стоит ли патч и поднят ли ADB (только чтение)
./adb-persist.sh verify [--device IP:PORT]

# Установить: бэкап → патч → проверка → remount ro
./adb-persist.sh install [--device IP:PORT] [--reboot] [--dry-run] [--force]

# Снять: вернуть стоковый onboot.sh из бэкапа, удалить эталон
./adb-persist.sh uninstall [--device IP:PORT] [--reboot] [--backup-dir DIR]
```

Установка делает бэкап (`onboot.sh`, `activate_adb.sh`, `launch.json`,
`rootkeeper.sh`) в `./backups/<timestamp>/`.
Флаг `--dry-run` выполняет только чтение+сборку, без записи.

Новое устройство сначала прогони через `install --dry-run`: скрипт сам
откажется, если якоря не совпадут.

## Границы и риски

- **L3 после wipe.** Патч гарантирует LISTEN :5555, но не сеть: после
  сброса станция не в домашнем Wi-Fi (S40wifi подсунет стоковый конфиг).
  Подключаться надо через setup-сеть станции — сканируй :5555 или смотри
  DHCP-таблицу роутера после онбординга.
- **OTA обновление сотрёт патч** (перезаписывает `/system`), но маркеры
  в `/data` переживут обновление — ADB, скорее всего, поднимется и на
  стоковой прошивке. Переприменение после OTA — снова одна команда
  `install`.
- **Полный wipe на железе не тестировался** (только удаление маркеров +
  rootkeeper с ребут-тестом — восстановление подтверждено на обеих
  моделях). Настоящий сброс потребует заново онбордить станцию.
- При установке скрипт никогда не оставляет `/` в `rw` (trap на выход).
- Откат в любой момент: `uninstall` из `./backups/`.

## Состав

- `adb-persist.sh` — один самодостаточный скрипт (патч встроен).
- `patches/onboot-adb-persist.patch` — тот же патч отдельным файлом,
  для ревью.
- `backups/` — сюда складываются бэкапы (в git не коммитятся).
